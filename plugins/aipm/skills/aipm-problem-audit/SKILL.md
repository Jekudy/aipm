# Purpose

Проверить описание проблемы из продуктового документа по заранее заданному чек-листу бинарных вопросов и вынести вердикт: дальше нельзя, идти можно с оговорками или готово. После вердикта — закрыть пробелы уровня MVP субагентами.

# When to use

Продакт принёс описание проблемы (ссылка на Confluence или локальный файл) и просит проверить, хватает ли его для работы. Скилл отвечает на вопрос «достаточно ли описана проблема», а не «хорошая ли это проблема».

# When not to use

Не для аудита решения, PRD или требований — там другой контракт. Не для оценки самой идеи: скилл проверяет полноту описания, а не ценность проблемы.

# Жёсткие правила

- Вопросы чек-листа нельзя переписывать, добавлять или убирать под конкретный документ. Чек-лист один для любой проблемы любой команды.
- «Да» ставится только с дословной цитатой из документа. Пересказ не считается.
- «Частично» не бывает. Ответ бинарный: «да», «нет» или «н/п» по зависимости.
- Спорный случай считается «нет». Конфликтующие места документа не разрешаются выбором удобного.
- Цитата короткая — одна-две строки, дословно. Если доказательства нет, пиши «не найдено: где искал» с указанием разделов, которые проверил.
- Зависимости: если вопрос-родитель получил «нет», все его дочерние вопросы получают «н/п» и не проверяются.
- Цитата должна доказывать именно проблему: фрагменты из разделов про выбор решения, план работ, оценку вариантов и черновые/песочные блоки засчитываются, только если в них описана боль, а не само решение.
- Дочерние вопросы проверяют артефакт родителя, а не любой похожий: значение — у метрики из MET-1, единицы и источник — у числа из VOL-1.

# Часть 1. Аудит

Протокол — три независимых прогона субагентами в свежем контексте, затем механическое сведение. Одиночный прогон не выдаёт вердикт: один и тот же документ в разных прогонах даёт разные ответы, поэтому «да» засчитывается только при 3/3.

1. Открой документ. Для ссылки Confluence используй `confluence-mcp`; для пути — локальный файл.
2. Прочитай [checklist.md](references/checklist.md). Запусти три независимых прогона (каждый — субагент в свежем контексте): все вопросы по порядку, сверху вниз. Порядок менять нельзя. Артефакты (run1–3.md, итоговый отчёт) сохраняй в каталог рядом с исходным документом или туда, куда указал пользователь.
3. Каждый прогон выводит таблицу:

   | ID | Вопрос | Ответ | Цитата / где искал | Уровень |

   Ответ: «да», «нет» или «н/п». Для «да» — дословная цитата. Для «нет» — «не найдено: <разделы, которые проверил>». Для «н/п» — «родитель ID = нет».

4. Обязательная механическая сверка каждого прогона: `scripts/check_quotes.py <отчёт.md> <источник.md> <чеклист.md>`. Скрипт проверяет полноту (каждый ID ровно один раз — пропуск строки отменяет вердикт), выводит каждое «да», чья цитата не найдена дословно (BAD), и каждое «да», чья цитата совпадает с цитатой другого вопроса в том же прогоне (DUPQUOTE). Не выдавай вердикт, не прогнав скрипт.
5. Ремонтный проход (один раз): для каждой BAD- или DUPQUOTE-строки либо скопируй дословный фрагмент из источника, либо поменяй ответ на «нет». Для DUPQUOTE сверь цитату именно с «Да, если» своего вопроса — найти фрагмент недостаточно. Прогони скрипт ещё раз: всё, что после этого прохода помечено, скрипт понижает до «нет» автоматически.
6. Сведение прогонов — только скриптом `scripts/aggregate_runs.py <чеклист.md> <run1> <run2> <run3>`: «да» засчитывается при 3/3; при 1–2 «да» итог — «нет» с пометкой «спорно, k/3», и пользователю показывается, в каком прогоне ответ отличается и чем. Если все три прогона совпали дословно, независимость формальная — пометь это в выводе: одинаковые таблицы снижают ценность сведения.
7. Вердикт выводит aggregate_runs.py:

   - Хотя бы одно «нет» на уровне MVP → **«Дальше нельзя»** + список проваленных MVP-вопросов с их «что дописать» из чек-листа.
   - «Нет» только на уровне ПОСЛЕ-MVP → **«В MVP идти можно, до масштабирования закрыть: …»** + список.
   - Все ответы «да» или «н/п» → **«Готово»**.

8. Вердикт относится к полноте описания проблемы. Он не оценивает решение, не обещает успех и не заменяет ревью решения.

# Часть 2. Улучшение

После вердикта предложи пользователю закрыть пробелы. Работай только с явного согласия.

1. Один субагент на один проваленный вопрос уровня MVP. ПОСЛЕ-MVP пробелы перечисли, но субагентов на них не запускай без отдельной просьбы.
2. Задача субагента: написать недостающий кусок текста только из документа, страниц по ссылкам из документа и данных, на которые документ указывает. Самостоятельное дискавери запрещено: новые исследования, расчёты и интервью не проводить.
3. Каждая фраза текста субагента обязана иметь локатор на источник — страница, ссылка или раздел. Фраза без локатора превращается в `нужно от PM: <что именно>`.
4. То, что может дать только продакт — решение, приоритет, доступ, договорённость — субагент не выдумывает, а помечает вставкой `нужно от PM: <что именно>`.
5. Приёмку делает другой агент в свежем контексте, не автор текста. Он проверяет отрывок тем же вопросом чек-листа: принимается, только если ответ «да» с дословной цитатой из отрывка, и каждый локатор в отрывке существует в источниках.
6. Собери принятые куски в один список правок по структуре документа. Не вставляй в документ без явной просьбы.

# Definition of done

- прогнаны все 34 вопроса по порядку, ни один не пропущен и не переформулирован;
- каждое «да» подтверждено дословной цитатой, каждое «нет» — записью «не найдено: где искал»;
- вердикт выведен по правилам части 1;
- улучшение запущено только с согласия, один субагент на один MVP-пробел, приёмка — тем же вопросом.
